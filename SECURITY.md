# Security

## What this server is allowed to do

It runs locally over stdio and is **read-only toward the game and every remote service**.

It never: scrapes RSI, Erkul, SPViewer or SC Trade Tools; reads game memory; sends keys or automates the game;
writes in the game folder; extracts `Data.p4k`; or calls any remote write endpoint, including UEX data
submission. The only writes are local: the cache, wiki snapshots, and the fleet file.

**Live telemetry is opt-in and off by default.** The game has an undocumented local gRPC server
(`GRPC_CLIENT_SERVER_ENABLED`). This server can read it only when the user sets `SC_TELEMETRY=on` in its
entry; the game-side variable is set by a command the user runs (`npm run telemetry -- enable --apply`; without
`--apply` it only shows what it would do, and `disable` removes only what it set), never by the installer. Without
`SC_TELEMETRY=on` no gRPC/HTTP2 code is loaded and no connection is attempted. When on, it connects only to
`127.0.0.1:2942` (fixed in code, not configurable), sends only the empty `TelemetryStream` request, keeps
frames in memory, and never logs, writes or transmits them. What it reads, what it does not, and the risks of
using an undocumented game feature are in [docs/TELEMETRY.md](docs/TELEMETRY.md); read its Risks section first.

Contacted hosts are fixed in `src/core/http.ts` (plus the opt-in loopback telemetry port above, which is not a host and not HTTP): `api.uexcorp.uk`, `api.uexcorp.space`,
`api.star-citizen.wiki`, `star-citizen.wiki`, `starcitizen.tools`, `api.github.com`,
`raw.githubusercontent.com`. Nothing else, and no analytics or usage reporting of any kind.

## Threat model

| Threat                                                                                                                                                         | Defence                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Token leak.** The UEX token sent to the wrong host, through a redirect, an absolute URL or a configured base URL                                             | Hard-coded host allowlist per upstream, checked on every request and every redirect; https only; the token is attached per request after that check, never stored in default headers; base-URL overrides must be on the same allowlist or startup fails; the token lives in `.env` next to the package, never in the Claude config; tests prove no token reaches a non-allowlisted host                   |
| **Prompt injection through data.** Marketplace ads, wiki and website text, contract titles, the maintainer's changelog, the patch-dump repository and what a remote server says in an error can contain text aimed at the model | Every result carries `trust`. Third-party text is marked `untrusted_text`: every string and key is stripped of invisible characters, shortened and shown with a notice that tells the model to treat it as data; text that is a whole answer is fenced between `<<<UNTRUSTED_TEXT source=...>>>` and `<<<END_UNTRUSTED_TEXT>>>`. Invisible characters are removed by Unicode category (format, private-use, surrogate, unassigned, control, variation selectors, so also the tag block U+E0000-E007F used to hide a sentence, bidi controls, zero-width and soft hyphen) plus the blank letters no category sees (combining grapheme joiner, Hangul and Khmer fillers, braille blank); NEL and line or paragraph separators become a newline. A `<<<` or `>>>` inside the text is replaced by look-alike guillemets after that cleaning, so the text cannot forge the end of a fence. Errors are covered too: what a remote server said (UEX status and message, wiki error text, an error body) is cleaned, cut at 300 characters and fenced inside our own sentence, and no error message keeps an invisible character. Game and build versions from a third party are cleaned and bounded at 80 characters where they enter (a patch-dump tag that is not a plain build string is dropped). A tool whose answer holds rows or free text from a third party is declared `untrusted_text` (the patch-dump tools and the UEX tools that return rows unprojected included); a test per source fails if free text reaches a `structured` tool. This lowers the risk; it cannot remove it: do not give the model tools that act on what a listing says |
| **Stale data presented as fresh**                                                                                                                              | `fetched_at`, `cache_age`, `data_age`, `stale`; an outage serves old data only when flagged; 4xx errors never fall back to cache                                                                                                                                                                                                                                                                                       |
| **Source changes its format**                                                                                                                                  | Files are validated for the fields we read; an unsupported schema or changed shape is an explicit error, not an empty answer                                                                                                                                                                                                                                                                              |
| **Supply chain**                                                                                                                                               | `npm ci --ignore-scripts`; lockfile committed; `npm audit` (production, high+) and `npm audit signatures` block CI; actions pinned by commit SHA with `contents: read`; Dependabot for npm and actions; secret scanning and push protection on; nothing is published                                                                                                                                      |
| **Game log privacy**                                                                                                                                           | Off by default; only `*.log` files; read-only and lock-free; no network code in the module; the player's handle, account id and paths are never captured; shown paths are shortened to three parts. The trade journal (`sc_trade_journal`) reads shop and cargo lines, keeps no player id, shop id, kiosk id or handle (the location lines that carry the handle are read for the location token only), and returns shop and item names only if they are plain identifiers; its one network use is the wiki's public commodity list (the same request for every user, matched locally on the commodity GUID, so nothing from the log is sent; names are cleaned and cut at 60 characters; `resolve_names` false disables it). Its answer is `untrusted_text`. The connection state (kicked, menu, online) is read from the end of the log: one `stat` per poll, only the added bytes, markers matched on the line's own tag, only a state, a time and a numeric code reach the tools                                                                                                                                                                                                        |
| **Local file tampering** | The fleet file is refused if corrupt or from a newer version rather than overwritten; writes are atomic; dataset names reject `/`, `\`, `..` and `:`; a collection name used in the build cache must be letters, digits, `_`, `-` and `.` without `..`, and the resolved path must stay inside the cache folder |
| **Any local program reads the telemetry.** The stream is unencrypted, has no token, accepts several clients and carries health, ship state and the aUEC balance | Not preventable by this server: it is the game's feature. Loopback only (not reachable from the network). Off by default. `docs/TELEMETRY.md` says it plainly. This server never logs, stores or sends frames; its diagnostics hold field numbers only |
| **The dashboard View: text from the stream or from the model reaches a page, and the page talks to the host** | One self-contained page, no network, with its own restrictive content policy; every string is set with `textContent`, never as markup; names from the stream are only game identifiers (`normalize.ts`); the route `plan` from the model is cleaned and capped on the server and again in the page; a `postMessage` from any window but the parent is ignored; `ui/message` carries fixed texts (plus a ship identifier and, for the route button the player pressed, the balance, said in the text); `ui/update-model-context` never carries the balance and is limited to one per 30 seconds; the page cannot send anything to the game, writes nothing to disk and keeps no frame; the dashboard tools are not listed to text clients; tests run the shipped script against a fake host and a DOM that refuses `innerHTML`. We do not call it safe: it is a new surface and needs review |
| **Game-log text reaches the dashboard View (transport ledger).** Contract titles, places and goods names come from Game.log, which the game writes | Each string is cleaned by the server's one rule (invisible and direction-changing characters out, fence markers defused), capped at 80 characters for a title and 60 for a place or goods name, and cleaned and capped again in the page; the page sets it with `textContent` only. The log is read-only, lock-free and opt-in; the ledger holds at most 60 contracts and sends 10 (8 steps each) inside its own 26 000-character budget (which also holds the commerce section below); its balance-derived figures (gain, total, pace, planned against measured) are built only when the View asked for the balance and never enter `ui/update-model-context` or `ui/message`; the ledger is a section of the poll with its own hash, computed from the content sent (a hash of a version with amounts is never sent to a View that did not ask for the balance), and the channel between Views carries it only without the balance-derived fields, stripped by the sender and again by the receiver; the balance history behind them is in memory, 500 changes at most, and no tool returns it. The gain is a raw measure that mixes purchases, rewards and fines, and says so. Accepted exception, stated plainly: `sc_live_poll` stays declared `trust: "structured"` in `tools/catalog.ts` although its `ledger` section now carries free text from Game.log (titles, places, goods), exactly as it already carries the wiki ship sheet. The reasons it is accepted: the tool is for the View only (`visibility: ["app"]`, not listed to text clients), the text sits in `structuredContent`, which the host does not add to the model's context, never in the fixed text of the answer or in a message to the model, and it is cleaned, capped and shown as plain text. The test that no source's free text reaches a `structured` tool covers UEX and wiki rows, not this poll. This lowers the risk; it does not remove it |
| **The commerce card shows amounts of the player's trades, and text from the model and from a log reaches it.** Transactions (amounts, goods, shops), the plan and its price points | Every amount of a run (turnover, cost, margin, fees, net, pace, projection) lives under `trade.runs[].money` in the ledger section, built by the server only when the View asked for the balance; without it the section holds goods, places, SCU, times and counts only. The history of balance changes is read only then. The channel between Views and the hash follow the ledger's rule and more: `ledgerStripBalance` (sender) and `ledgerChannelClean` (receiver) drop `money`, tests read the wire for the made-up amounts, and `ui/update-model-context` and the fixed messages never carry the run. Labels from the journal (goods, shops) are cleaned by the server's one rule and capped at 60 characters; the plan's text and numbers are cleaned and bounded on the server and again in the page (at most 30 price points, each finite and bounded); everything is set with `textContent`, the chart is built with `createElementNS`, no markup string. The model of the run is pure: no file, no network, the dashboard never calls UEX (the price points come from Claude), and no Game.log parser was added (the commerce lines are read by the existing `providers/gamelog/trade.ts` through the ledger's bounded, incremental reads: at most 3 000 lines kept). A fee is reported as measured only when a balance change matches a transaction within a short window, otherwise it is labelled an estimate or unknown; the window and the 8 s settle delay are assumptions not yet measured with the real game |
| **Wiki text shown in the dashboard View (the ship sheet)** | The ship's name, version and date come from the Star Citizen Wiki, which anyone can edit. They are cleaned (`core/untrusted.ts`), capped (60 characters, 8 candidates) and bounded on the server, and set with `textContent` only; figures are positive bounded numbers (0 means not provided); the lookup runs in the background through the guarded client on a host already on the allowlist, once per ship, never while telemetry is off, and the class name sent to the wiki is a game identifier of a known maker or nothing is sent; the sheet travels in `structuredContent` only, never in the fixed text of the poll or in a message to the model. A wrong or edited sheet can still draw a wrong scale: it is labelled "wiki", dated, and a ship that fits several sheets gets none |
| **Many dashboards poll at once** (the host keeps every one it mounted) | One shared answer per 500 ms; only the most recent visible View polls (leader election, see the next line); a View stops when hidden, off screen, torn down, or after 30 minutes away; never more than two requests a second; the reader still stops after five idle minutes |
| **The channel between dashboards** (`BroadcastChannel`, same sandbox origin: any page of that origin can post on it) | Everything that arrives is data, never an instruction and never an approval: type, identifier, rank (not in the future), visibility and the shared answer are checked, and the answer is rebuilt field by field (known fields, right types, capped lengths and counts; names must be game identifiers). It never reaches the `postMessage` handler of the host, which only believes its parent window. The balance and the wallet events never go on the channel, only the leader sends `ui/update-model-context`. A hostile page of the same origin could still take the lead and stop other dashboards from polling (a nuisance, not a leak); the take-over button answers it. The channel is not governed by the content policy and sends nothing over a network. Not verified in Claude Desktop |
| **A local program pretends to be the game** on port 2942 and sends hostile frames (crafted protobuf, huge or endless messages, text aimed at the model in names) | Hand-written decoder with hard limits: message 1 MiB (checked on the header, before the body is buffered), 5 000 fields per frame (a frame over it is refused), 64 weapons, 16 countermeasure entries and 32 game events per frame (the surplus is not decoded and an anomaly is noted), wire types, depth by schema; at most about 33 frames a second are decoded (the newest frame of a burst is never lost; the ones in between are counted but not decoded); the framer buffers chunks in a list and joins them once per message; event data is cut to 80 characters and the ring holds 200 events; an answer of `sc_live_state` or `sc_live_events` is cut under 40 000 characters (the payload, before the provenance envelope) and says so; one bad frame never stops the stream; five bad frames in a row make the state `incompatible`; strings from the stream are only passed on if they look like a game identifier (`[A-Za-z0-9_.-]`, 64 characters), otherwise replaced; diagnostics sets are bounded; sections keep their last value for 3 seconds only |
| **The aUEC balance reaches the model provider.** Tool results are part of the conversation | The balance is withheld unless the caller asks (`include_balance`); balance-change events are hidden by default; the prompts and `docs/USING_WITH_CLAUDE.md` tell Claude to ask the player first and to say where the figure came from |
| **Telemetry enabled without the user's knowledge** | Two explicit switches, neither set by installing or updating; `npm run telemetry -- enable` is a dry run unless `--apply`; without `SC_TELEMETRY=on` no HTTP/2 code is loaded and no connection is made (`npm run check:telemetry-silence` proves it on the built server; a test proves the module graph); the address is a constant in code |
| **The telemetry command damages the Claude Desktop configuration** | The file is edited as text: only the `SC_TELEMETRY` key is inserted, changed or removed (CRLF, indentation, numbers, BOM kept); if the result is not exactly what was expected nothing is written and the line to add by hand is printed; timestamped backup first; atomic write; tests use temporary files and a fake environment store; no secret is ever printed |
| **The installer damages the Claude Desktop configuration, or prints a secret from it** | `npm run install:claude` edits the file as text like the telemetry command: only the `sc-copilot` entry is added or replaced (CRLF, indentation, BOM and number spellings such as `1.0` or integers above 2^53 of every other server are kept); if the result is not exactly what was expected nothing is written and the entry to add by hand is printed; dry run unless `--apply`; timestamped backup first; atomic write. The preview of an entry already in the file shows the names of its `env` keys, never their values (any other key and any argument that names a secret are hidden too) |
| **Reading the game's undocumented feature has consequences with the publisher** | Not a technical defence and not ours to settle. `docs/TELEMETRY.md` (Risks) states that the feature is undocumented, that CIG has neither allowed nor forbidden it to our knowledge, that the game can see that a client is connected, and that the risk is the user's. Nothing in this project calls it safe, undetectable or approved |
| **Hostile contribution.** Prompt injection in docs, prompts or tool descriptions; hidden characters; poisoned dependency | A human reviews every pull request, whoever or whatever wrote it. `npm run check:docs` runs in CI and in the tests: it refuses invisible, bidi, tag and lone carriage-return characters, HTML comments and active tags, invisible Markdown (comment-style link definitions, link titles), look-alike letters of any non-Latin script or of a compatibility form, links to hosts or GitHub projects that have not been reviewed (in documents, configuration and code), and translations that change an identifier; it also reports hooks, lifecycle scripts, network commands in `package.json` scripts and lock file entries outside the npm registry. It does not catch hostile text written in plain sight: only the review does (list in CONTRIBUTING.md). Same dependency rules as for the supply chain: no new dependency without a reason, no install script, no native code in production dependencies (development tools ship prebuilt native binaries, see CONTRIBUTING.md) |
| **Another project's `.env`**                                                                                                                                   | Only the `.env` next to the package is read, never the working directory's                                                                                                                                                                                                                                                                                                                                |

## Unverified: extracting game files

Whether extracting `Data.p4k` (with community tools) could affect an account was researched and **not
established**: no statement from CIG on the subject was found, and no report either way about Easy
Anti-Cheat and offline file reading. Reading files from disk is not what anti-cheat watches (memory, injection),
but that is a general expectation, not a verified fact for this game. This project therefore ships no extraction
code and gives no instructions for it. If you do it yourself, you accept that risk.

## Repository protection

Set on GitHub, not in the code, so the review rule in the threat model is enforced and not only promised:

- A ruleset on `main`: changes arrive by pull request only (squash merge), the four CI checks must pass (lint, tests
  and build on Ubuntu and Windows; dependency audit; CodeQL analysis), and force pushes and deletion are refused.
  No one is exempt from it.
- Workflow runs of pull requests from outside contributors wait for a maintainer's approval, every time.
- Only GitHub Actions pinned by commit SHA may run.
- Private vulnerability reporting, secret scanning with push protection, Dependabot alerts and CodeQL are on.

A maintainer who is alone on the project reviews their own changes with the CI and with independent read-only review
passes; there is no second human. That is a limit, and it is stated here on purpose.

## Reporting a vulnerability

Open a private security advisory on this repository (Security tab, "Report a vulnerability"), or contact the
maintainer through GitHub. Please include the tool or file, what you expected, what happened, and a minimal
reproduction. Do not include real tokens or personal logs.
